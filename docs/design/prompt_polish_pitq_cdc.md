# Prompt：润色技术设计文档 — PITQ & CDC for IVM

## 任务

润色和重组技术设计文档 `docs/design/pitq_and_cdc_design.md`，使其更容易被不同角色的读者理解，从而高效推动对齐和决策。不要改变技术内容的正确性，重点是重组结构、调整信息密度和突出关键信息。

## 背景

这篇文档讲的是：StarRocks 要在存算分离内表上支持增量物化视图（IVM），IVM 依赖两项底层能力——历史版本查询（PITQ）和变更数据捕获（CDC）。文档围绕 MVCC、PITQ、CDC 三条线，设计了从 IVM 最小需求出发的短期方案，以及面向 Time Travel / 通用 CDC 的长期演进路径。

| 读者 | 核心关注 | 阅读深度 |

| CTO | 为什么做、产品价值、竞品对标、投入产出比、roadmap 节奏 | 读摘要 + 动机 + roadmap，不会深入技术细节 |
| 查询团队 Leader | 对查询架构的影响面、FE/CN 侧改动范围、性能影响、技术风险 | 会看方案设计的架构级描述，关注对现有查询流程的侵入性 |

## 润色目标

### 结构目标

按以下逻辑主线重组（不一定严格对应章节，但信息流要符合这个顺序）：

1. **摘要**：保持当前风格——简洁点出问题、长期价值、本文目标。让读者知道这篇文档要讨论什么，不需要附带结论或方案概述。
2. **动机与价值**：当前第 2 章内容基本 OK，精简即可。竞品对标表格保留。
3. **需求分析**：当前第 3 章。核心是讲清楚 IVM 的需求边界以及与通用场景的差异。当前写得较好，但 3.1/3.2 中 IVM vs 通用场景的对比表格可以更紧凑，减少重复文字描述。3.3 的总结是后续所有方案设计的需求基线，可以适当强调。
4. **方案设计**：当前第 4-6 章是核心。重组要求：
   - 对于已经确定的方案，保留简明的推导过程和关键理由，让读者能跟上思路，但不需要事无巨细地展开每一步
   - 对于需要决策或有显著 tradeoff 的地方，自然地在行文中体现出这是一个需要权衡的选择，不需要加特殊标记或格式
   - 当前的示例和图非常好（如 4.4 的 MVCC 示例、6.6.2.2 的 Changes Vector 示例、6.6.2.3 的 Net Changes 完整示例），这些帮助理解的关键素材要保留，但可以适度精简，确保每个示例都有明确的目的
   - 6.6.3 Snapshot Diff 和 6.6.4 并行 Scan 是中期能力，在主文中用适当篇幅介绍思路即可
5. **Roadmap**：当前第 7 章。在每个 Phase 增加预估工期和依赖关系的说明（如果原文没有，标注为 TBD 提醒作者补充）。
6. **附录**：当前附录内容很好，保留。只有在主文确实过长的段落才考虑移到附录，不要过度搬迁。

### 风格目标

- **自然流畅**：读起来像一个资深工程师写的文档，不要有 AI 润色的痕迹。避免过度结构化（比如每段都用粗体开头）、避免刻意的排比句式、避免不必要的总结性段落。
- **直击核心，不啰嗦**：一个概念只在一个地方定义，后续引用时只给指针。当前"IVM 的需求简化"在需求总结和短期方案开头都有重复描述，合并。
- **分层信息密度**：主文保留推导过程的核心脉络（问题 → 思路 → 方案 → tradeoff），但砍掉过于细节的推导步骤。让快速读者能在 15-20 分钟内读完主文（不含附录），深入读者可以进入附录看细节。
- **上下文注释**：对于非本领域的读者可能不熟悉的概念（如 GTID、visible version、tablet metadata、CatalogRecycleBin 等），在首次出现时给一句话解释，不要假设所有读者都了解存算分离内表的实现细节。
- **保留技术深度**：这是一篇面向资深工程师的设计文档，不是 PPT，技术深度是它的价值。润色是让深度更容易被消化，不是删掉深度。

### 具体改进点

以下是我观察到的一些具体问题，供参考（你应该自己判断是否合理以及是否还有其它问题）：

1. **4.2 现状与差距**和 **4.4 短期方案**有信息重叠：4.2 分析了差距，4.4 又重新说了一遍"IVM 的需求特点使得可以绕过"。可以合并为更紧凑的叙述。
2. **4.3 和 4.4 的顺序**：当前先讲长期方案（4.3）再讲短期方案（4.4）。对于一篇以 IVM 短期交付为首要目标的文档，考虑先讲短期方案（读者最关心的），再讲长期方向。
3. **6.6.2.2 主键表方案对比**：三个方案的 tradeoff 分析是本文重要的设计决策之一，当前的对比较清晰，但可以考虑用更紧凑的方式呈现（比如对比表格）让结论更直观。
4. **6.6.2.3 Net Changes 的完整示例**（约 150 行）：非常好的示例，但在主文中占比较大。考虑保留核心思路描述和一个简化示例，完整的三次导入示例可以移到附录。
5. **版本可观测（4.5）**：在当前文档中显得孤立且优先级不高，可以并入 roadmap 或简化。
6. **4.4 短期方案开头有重复段落**："IVM 场景的需求简化（详见 3.3）使得短期可以绕过..." 和 "IVM 场景的需求特点使得短期可以绕过..." 是两段说同一件事，明显是编辑遗留。
