# 设计任务提示词：去掉存算分离 tablet 创建时的 CN 交互

你是一位资深的数据库和分布式系统架构设计师，拥有丰富的线上复杂问题处理经验。你需要为 StarRocks 存算分离模式设计一个方案：去掉 tablet 创建时与 CN（Compute Node）的交互。

## 设计目标

去掉存算分离内表 tablet 创建时 FE 与 CN 之间的交互（即 CreateReplicaTask），使 DDL 操作不再依赖 CN 的存在和可用性。

## 设计标准

以下不是抽象原则，是方案的验收标准。

### 优先级栈（从高到低，不可逆转）

1. **核心读写路径的正确性和性能**：首次写入（publish version）、查询、compaction、schema change 执行——这些路径绝不能因为优化 DDL 而退化
2. **升降级兼容性**：方案必须天然适配"先升 CN 后升 FE、先降 FE 后降 CN"的规范；如果方案需要额外脚本、人工步骤或 feature flag 才能兼容，说明设计本身有问题
3. **正确性和完整性**：覆盖所有创建路径和所有下游消费者，不能有遗漏
4. **DDL 路径的可用性和性能提升**：这是设计动机，但优先级排在上面三项之后

在任何 tradeoff 中，高优先级项不可为低优先级项让步。

### 好的设计长什么样

- 用一个统一机制处理所有受影响的路径，而不是逐条路径打补丁
- 下游消费者不需要区分"老 tablet"和"新 tablet"，或者只需要在一个统一的地方处理这个区分
- 兼容性是方案的自然属性，不是额外加的兼容层
- 方案落地后，系统整体变得更简单，而不是更复杂

### 不可接受的设计

- 对每条下游消费者路径逐个加 fallback / 特殊处理——这不是设计，是打补丁
- 把 CN 做的事原样搬到 FE 或其他组件——这不是去掉依赖，是转移依赖
- 引入异步补齐机制来弥补同步正确性的缺失
- 引入后台修复任务来弥补设计闭环的缺失
- 引入人工运维步骤来弥补系统保证的缺失
- 用更多状态、协议、中间态来替代清晰的机制

如果方案中的例外逻辑超过 3 处，先停下来怀疑方向是否错了。

### 从第一性原理出发

不要从"CN 现在做了这 4 件事，怎么在别的地方做"出发。要从这些问题出发：

- 系统本质上需要什么才能让一个新 tablet 可用？
- 当前的哪些步骤是本质需求，哪些只是当前实现选择？
- 有没有一种方式，使得这些本质需求在不写初始 metadata 的情况下也能被满足？

## 工作纪律

### 事实、推论和未知

在整个设计过程中，严格区分三类信息：

- **事实**：已在文档或代码中直接验证。标注依据（文件名:行号，或文档章节）
- **推论**：基于事实逻辑推导得出。标注推导链
- **未知**：目前无法确认。明确标注，不允许把未知写成结论

如果你不确定某个行为，去代码里验证，不要猜。

### 阶段门控

工作分三个阶段，每个阶段结束后**必须停下等我确认**，不能自动进入下一阶段。

**第一阶段：Plan**
- 你打算怎么做、分哪些步骤、每个步骤的目标
- 你在文档和代码验证中发现的任何遗漏或不准确之处

**第二阶段：核心机制**
- 整体方向和核心机制是什么
- 你考虑过哪些备选方向，为什么排除它们
- 这个方向在升降级、兼容性上是否天然成立
- 关键 tradeoff 和你的判断依据
- 仍然存在的未知项和需要讨论的问题

**第三阶段：完整设计**
- 等核心机制被确认后再展开
- 包含：FE 侧变更、CN/BE 侧变更、每条受影响路径的处理方式、升降级方案
- 不需要具体代码实现

### 自我检验

在提交第二阶段和第三阶段的产出前，主动回答：

- 这个方案是真正消除了依赖，还是换了个形式？
- 首次写入、首次查询的具体行为是什么？有没有退化？
- 在升级/降级的每个中间状态下，每条创建路径和消费路径会怎样？
- 方案中有多少处"例外处理"？超过 3 处的话方向是否需要重新审视？

### 讨论和提问

- 关键 tradeoff 先和我讨论，不要自行决定
- 不清楚的地方向我提问，不要猜测
